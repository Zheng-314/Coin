# 数据与工程质量修复记录

本轮针对项目做了一次系统排查，修复了 5 个问题。每一条都给出了问题证据、修复方式和验证方法。

## 一、后端无法启动（致命）

**问题**：`backend/app_new.py` 第 8 行 `from flask_limiter import Limiter`，但
`requirements.txt` 里没有 `Flask-Limiter`，环境中也未安装。
结果是后端在此环境下**完全无法导入**，整个服务起不来。

**修复**：
- `requirements.txt` 补入 `Flask-Limiter==4.1.1`、`fpdf2==2.9.0`、`opencv-python-headless`
  （后两者分别被 `routes/report.py` 的 `from fpdf import FPDF` 和图像处理使用，同样缺失）

**验证**：
```
python -c "import app_new; print(len(list(app_new.app.url_map.iter_rules())))"
# 输出 29
curl http://localhost:5001/api/health
# {"message":"服务正常运行","status":"ok"}
```

## 二、数据集划分泄漏（影响所有指标）

**问题**：`training/kinds/model/split.py` 用 `train_test_split` 对**行**随机切分。
而 `make.py` 为同一枚钱币生成了 5~9 行（原图 + gs/jy/rd 增强副本），
按行切分导致同一枚币的增强副本同时进入训练集和验证集。

**实测重叠**：

| 任务 | 训练∩验证（同名图像） | 训练∩测试 |
|---|---|---|
| 品相 kinds | 8,129 张 | 14,495 张 |
| 分数 scores | 3,643 张 | — |

即验证集里混入了训练时见过的图像，99.69% / 99.70% 这两个指标包含记忆成分。

**修复**：新增 `scripts/split_dataset.py`
1. 文件名归一化到钱币编号（`0gs.jpg` / `0jy.jpg` / `90016gs1.jpg` → 前导数字）
2. 并查集求连通分量（存在少数图像被两个钱币对共用的情况）
3. 以连通分量为单位整组切分，按标签分层
4. 切分后校验「图像」与「钱币」两级重叠必须为 0

**验证**：
```
python scripts/split_dataset.py --dry-run
# 品相 54,525 / 7,806 / 15,594 行，钱币 10,722 / 1,532 / 3,064
# 重叠 图像 train∩val: 0  train∩test: 0  val∩test: 0
# 重叠 钱币 train∩val: 0  train∩test: 0  val∩test: 0
# 结论: ✅ 无任何跨集合重叠
```
切分后三集合行数之和为 77,925，与 `data.csv` 完全一致，无样本丢失。

**顺带发现**：`make.py` 中 `gs-jy` 组合被写了两遍（相邻两行完全相同），
造成该组合样本被重复计入。可用 `--dedupe-identical` 去除。

## 三、知识语料含大量无意义文本

**问题**：`data/artifacts/text_units.parquet` 221 篇中有 74 篇内容只有一行
`PCGS #709846`。这类文本不携带语义，进入 GraphRAG 后会抽出 `709846` 这种噪音实体
（已在现有图谱中确认存在），并稀释向量检索召回。

**分类结果**：

| 类型 | 篇数 | 字数 |
|---|---|---|
| 实质条目 | 144 | 22,441 |
| 纯编号 | 74 | 888 |
| 术语表 | 1 | 243 |
| 单字段 | 1 | 14 |
| 过短 | 1 | 12 |

**修复**：新增 `scripts/clean_corpus.py`，输出
`text_units_clean.parquet` / `.csv`（保留 144 篇）与 `text_units_dropped.csv`（剔除清单，便于复核）。

## 四、hf-space/backend 与 backend 代码漂移

**问题**：两份代码手工维护，hf-space 那份缺了限流器、缺了同源前端伺服、
向量库报错信息也不同。漂移会导致"本地能跑、部署不行为"难以定位。

**修复**：新增 `scripts/sync_hf_space.py`，只同步 Python 源码，
自动跳过 `.env`、`instance/`、`venv/`、`__pycache__`、`*.log`、`*.onnx` 与 `.DS_Store`。

**验证**：同步后 `--dry-run` 报告「两份代码已一致」。

## 六、蓝图只在 __main__ 注册，导入即空应用

**问题**：`app_new.py` 把 `register_blueprints()` 放在 `if __name__ == '__main__'` 里。
`from app_new import app` 拿到的是一个**没有任何 /api 路由**的 Flask 应用
（只有 health、根路由、static 共 3 条），导致测试中 18 个用例全部返回 404。
`server.py` 因为手动调了一次注册而幸免，属于两套启动路径行为不一致。

**修复**：
- 新增 `create_app()` 工厂函数，导入后显式调用即可拿到完整应用
- `register_blueprints()` 改为幂等（内部状态位），`server.py` 与 `__main__` 重复调用安全
- `tests/conftest.py` 改用 `create_app()`

**验证**：
```
导入 app_new          -> 3 条路由（未注册）
create_app()          -> 29 条路由
再次 register()       -> 29 条（幂等，无重复注册报错）
pytest backend/tests  -> 21 passed
```

## 九、鉴定功能：模型输出维度与分类体系不匹配（严重）

**问题**：部署的 `backend/best_model.onnx` 输出维度为 **26**，而分类体系
`classification.json` 已扩展到 **92 类**。`predict.py` 直接用模型输出的下标去索引
92 个类别名，导致两个后果：

1. 只会命中 `CLASS_NAMES[0..25]`，**其余 66 类永远不可能被预测出来**；
2. 显示的版别名称与模型实际预测语义无关，属于静默错误。

旁证：`predict.py` 加载失败时的兜底写的是 `[f"类别 #{i}" for i in range(26)]`，
说明这套代码原本就按 26 类设计，分类体系扩到 92 后模型没有重训重导出。

**实测**（取 `data/raw` 中 12 枚不同钱币）：

| 现象 | 结果 |
|---|---|
| 不同 Top1 类别数 | **1**（12 枚全部输出「吉林省造 > 辛丑 > 七钱二分」） |
| 置信度范围 | 18.76% — 63.19%，平均 38.31% |
| 92 类均匀分布基线 | 1.09% |

此外 12 次推理中 7 次选中 `swapped`（正反面交换后置信度更高），也是模型与输入约定
不匹配的迹象。

**已做的处理**：在 `/predict` 增加一致性校验，维度不等时返回 503 并说明原因，
不再输出可能错误的版别名；`/api/predict/capabilities` 新增
`model_output_dim`、`taxonomy_classes`、`class_mapping_ok` 三个字段。
临时演示可设 `ALLOW_CLASS_MISMATCH=1` 恢复旧行为。

**仍需完成**：用 92 类体系重新训练并导出模型，替换 `best_model.onnx`。
这是鉴定功能真正可用的前提，无法通过改代码绕过。
